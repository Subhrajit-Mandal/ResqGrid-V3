# Security and privacy boundary
Production verifies Supabase asymmetric JWT signatures, issuer, audience and expiry. Roles and verified active agency membership are loaded from PostgreSQL on every authorization; browser flags cannot grant staff access. Demo identities are rejected in production. A distinct `publish_alert` capability separates assessment from publication.

The API database login must be a member of `resqgrid_api`, with no ownership, superuser, bypass-RLS, role-management or auth-schema write privileges. Each API transaction sets verified actor context locally. Only the backend may use this credential. Browser Supabase roles have no business-schema grants. Do not expose `resqgrid` through Supabase's Data API. The worker login receives only `resqgrid_worker` permissions and no incident details/messages. Secrets reside in server/provider secret stores, never VITE variables, source, device examples or logs.

Operational incident summaries are jurisdiction scoped; exact location/submission is limited to the reporter and the assigned verified agency. Private reads are audited. Public warnings are explicitly sanitized. No real personal data belongs in the browser demo's localStorage. Live file uploads must use a private bucket, size/type/magic checks, malware handling, signed short-lived downloads, ownership checks and metadata stripping before enabling the UI. No file upload endpoint is included yet.

Implemented controls: strict Pydantic inputs, unit/range/time checks, authenticated WebSocket Origin checks, 64KiB mutating payload check, browser-safe errors, idempotency, row locks/version guards, immutable audit grants, TLS MQTT, topic/device registry validation, model artifact approval and checksum checks. Middleware currently buffers request bodies before size rejection; enforce streaming/body limits at the reverse proxy. In-memory API rate limits are single-process and need shared or edge enforcement before scaling. Add connection/IP budgets and broker per-device quotas.

Acceptance still required: run SQL migrations in a fresh test Supabase project, prove policies with distinct restricted logins, revoke inactive memberships during connected sessions, assignment races, token expiry, exact-location leakage, upload attacks, dependency audit, provider security headers/CSP, TLS/secret rotation, backup encryption/restore, audit retention and staff MFA. RLS policies and JWT paths have not been tested against real services here. No production-security certification is claimed.

Dependency review in this workspace: MapLibre upgraded to 6.12.0 and Vitest to 4.1.11 to address their published advisories. The final npm audit reports zero known issues for the installed lockfile, including development dependencies. This does not establish absence of vulnerabilities or replace Python dependency and application security review. References: [MapLibre advisory](https://github.com/maplibre/maplibre-gl-js/security/advisories/GHSA-jrc7-96c5-q579), [Vitest advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9). Render templates explicitly require production mode so missing service configuration cannot silently start the demo API.

## Frontend review sessions
The review UI implements browser-only role guards and a public shared demo password. This preserves simulated cross-role workflows and is not an operational authentication system. The password and role/session storage are editable by the browser user; do not use this mechanism for real data. Logout removes only the demo session, retaining fictional workflow data. Sessions expire after 12 hours; storage events synchronize logout across tabs. Optional agent scenario mutations require the demo admin role. Live Supabase/API permission checks above remain independent and unchanged.
